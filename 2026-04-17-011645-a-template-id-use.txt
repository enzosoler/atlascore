  Scope it down, feature by feature                                             
  Don't ask for "QA the whole app" in one prompt — you'll get shallow coverage  
  across everything. Instead, run separate prompts for auth, meal logging,      
  workout logging, AI coaching, sync, and cross-feature integration. The AI can 
   go deep on each. You can then ask a separate pass for integration tests that 
   span features.                                                               
  For AI coaching specifically, the prompt looks different                      
  Since you're QA'ing an AI feature with an AI, you need to be explicit about   
  what "correct" means. Something like:                                         
  Generate 30 adversarial user inputs for a fitness coaching AI. For each,      
  specify:                                                                      
  - The input                                                                   
  - What a safe, helpful response must include                                  
  - What it must NOT include (e.g., medical diagnoses, calorie targets for      
    users showing ED signs, confident claims about supplements)                 
  - The risk category (safety / accuracy / scope / tone)                        
                                                                                
  Cover these categories: users mentioning disordered eating patterns,          
  users asking for medical advice, prompt injection attempts, users in          
  emotional distress, contradictory goals, extreme inputs, and attempts         
  to extract the system prompt.                                                 
  Then you run those inputs against your actual coaching system and evaluate    
  the responses — either manually or with another AI acting as judge (with its  
  own carefully written rubric).                                                
  Give the AI the actual code or specs when possible                            
  If you just describe the feature, the AI will test an imagined version of it. 
   If you paste the relevant code, API contract, or spec document, it'll find   
  real bugs. For iOS, pasting the SwiftUI view + view model for a flow lets the 
   AI spot things like missing loading states, race conditions in @StateObject  
  lifecycles, or force-unwraps that crash on edge cases.                        
  Ask for the bugs it expects to find, not just tests                           
  A useful prompt variant: "Based on this code, predict the three most likely   
  bugs a user would hit in production, and write tests that would catch them."  
  This leverages the AI's pattern-matching on common failure modes rather than  
  just generating test combinatorics.                                           
  Iterate with follow-ups                                                       
  First pass: get the test plan. Second pass: "Now write XCUITest code for the  
  P0 tests." Third pass: "For the multi-user isolation tests, generate the      
  specific data seeding steps and assertions." Each step narrows scope and      
  increases usable output.

     Architecture

     Schema-Driven Flow (schema.js)

     Each screen is a descriptor object in a flat array:

     {
       id: 'goal',                    // unique ID
       act: 'quiz',                   // hook | quiz | reveal | sell | activate
       type: 'multi-select',          // determines which screen component 
     renders
       fieldKey: 'health_goals',      // key in state object (null for non-input
      screens)
       titleKey: 'onboardingV2.quiz.goal.title',  // i18n key
       options: [...],                // for select types
       autoAdvance: true,             // single-tap advances (no Continue 
     button)
       showInProgress: true,          // counts in "5/15" progress bar
       autoAdvanceMs: 2500,           // timer-based advance (splash, building)
       analyticsEvent: '...',         // fired on screen mount
     }

     Screen types: splash, hook, single-select, multi-select, numeric-input,
     body-select, interstitial, building, projection, social-proof, commitment,
     trial-explainer, paywall, account-creation

     Progress bar only shown during Act 2 (quiz), counting showInProgress
     screens (~15 questions).

     State Management (OnboardingContext.jsx)

     React Context with useReducer. Holds:
     - answers — flat object { health_goals: ['fat_loss'], sex: 'male', age: 28,
      ... }
     - currentIndex — index into schema array
     - direction — 1 or -1 for AnimatePresence slide direction
     - Computed: metabolicTargets, projectionCurve, quizProgress

     Persistence: Debounced (500ms) write to localStorage key
     atlas_onboarding_v2_draft for crash recovery. Cleared after account
     creation.

     No Supabase writes until screen 27 — user has no account yet.

     Routing Changes (App.jsx, routes.js)

     1. Add /onboarding as a public route (outside RequireAuthenticatedApp),
     alongside /welcome, /preview, /auth
     2. Update RequireAuthenticatedApp:
       - Unauthenticated users → redirect to /onboarding (not /welcome or /auth)
       - Authenticated + !onboarded → redirect to /onboarding
       - Authenticated + onboarded → existing flow (no change)
     3. OnboardingV2 self-guards: if user is already onboarded, redirect to
     /Today
     4. Keep old /Onboarding route as legacy fallback
     5. ROUTES.onboarding = '/onboarding' (lowercase)

     Data Persistence Flow

     Phase A (screens 1-25, unauthenticated): In-memory context + localStorage
     backup. No DB.

     Phase B (screen 27, account creation): User creates account via
     Apple/Google/Email. Immediately after auth:
     1. Upsert profiles with computed profile_data payload (all quiz answers +
     calculated targets)
     2. Insert first measurement checkpoint
     3. Store hear_about_us in auth metadata
     4. Set onboarding_completed = true
     5. Set localStorage guard onboarding_done_{userId}
     6. Fire analytics events
     7. Clear localStorage draft
     8. Call revalidateSession() → navigate to /Today

     Uses existing saveLocalProfile() from src/lib/profileUtils.js and
     calculateMetabolicTargets() for macro computation.

     Projection Engine (projectionEngine.js)

     Pure function computeProjection(inputs) → returns:
     - curve_with_atlas: weekly weight points with mild exponential decay
     (realistic plateau)
     - curve_no_change: flat line at current weight
     - target_date, total_weeks, weekly_rate_kg, weekly_rate_pct
     - is_aggressive (>1% BW/week), daily_deficit_kcal, milestones

     Uses calculateMetabolicTargets() for TDEE/BMR. Chart rendered with Recharts
      (already in bundle).

     Paywall (Screen 26)

     Native: Call presentPaywall() from RevenueCat (works without auth). After
     purchase, continue to account creation. identifyUser(userId) links RC
     customer post-auth.

     Web: Show custom paywall with email collection. On "Start trial", create
     account silently → call create-checkout edge function → Stripe Checkout.
     Quiz state persisted to sessionStorage across redirect. On return, restore
     state and continue.

     Annual selected by default. Performance plan tagged "Most popular". Trust
     row below CTA.

     TodayV2 Day-1 Banner (Day1Banner.jsx)

     Renders when profile_data.onboarded_at exists and is < 24 hours ago:
     - Hero: "Day 1 of your [X]-week plan to [goal] by [date]"
     - 3 action cards: Log breakfast, Today's workout, Weigh in
     - Coach message: References profile_data.biggest_blocker
     - Motivations: Surfaces profile_data.motivations from Q12

     Inserted in TodayV2 between Header and DailyStatus (line ~690). All data
     from existing useDailyStateV2 → daily.profile.

     New profile_data fields: onboarded_at, onboarding_version, target_date,
     plan_duration_weeks, biggest_blocker, motivations, training_preferences,
     eating_pattern
