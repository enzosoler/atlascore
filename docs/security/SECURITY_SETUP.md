### 5. Add server-side rate limiting on AI endpoints

The video from Chris covers this well. Recommended approach for Atlas Core:

1. Create a `rate_limits` table **separate** from your users table (so RLS on user data
   cannot be abused to change limits):

```sql
CREATE TABLE rate_limits (
  user_id    uuid PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  ai_calls   integer NOT NULL DEFAULT 0,
  reset_at   timestamptz NOT NULL DEFAULT (now() + interval '1 day'),
  daily_cap  integer NOT NULL DEFAULT 50
);
ALTER TABLE rate_limits ENABLE ROW LEVEL SECURITY;
-- Only service_role (edge functions) can write; users can only read their own row
CREATE POLICY "rate_limits_select_own" ON rate_limits FOR SELECT USING (auth.uid() = user_id);
```

2. In your AI edge function (Base44 function or Supabase function), check and increment
   this counter using the `service_role` key before forwarding to the AI provider.

- Sign-ins: limited (default 30/hour per IP is reasonable)

## 📌 Remaining medium-risk item

**Subscription enforcement is client-side only.** The `hasFeatureAccess()` function in
`src/lib/entitlements.js` runs in the browser. A determined user can unlock premium
features by modifying React Query cache. To fix this properly, your Base44 AI/export
functions need to verify subscription status server-side before processing the request.
This requires changes to your Base44 backend functions — out of scope for a code-only fix.
